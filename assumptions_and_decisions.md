# Evaluation app assumptions and decisions

## Confirmed in discussion

- **Participant task.** Participants start with an empty playlist and a text request they write themselves. The full session, including refinements, counts toward the comparison.
- **Input and playlist.** The same text box and shared playlist drive both panels. Users can keep suggestions and search public YouTube Music for songs to add directly. After the opening round, text can be paired with the current songs or left blank for playlist-only recommendations. Manual additions with blank text trigger a new round. Keeping a suggestion preserves the current offers so users can finish rating them.
- **Comparison.** Show team retrieval with one of the two baselines, with the left and right positions randomized and fixed within each session. Both panels receive the same playlist snapshot and request. Team testing can select one recommender explicitly.
- **Overlap.** Show shared recordings in both panels and mirror Keep or Reject. Keep inserts the recording into the shared playlist once. A verified catalog ISRC, a unique MPD track match, or an identical YouTube video ID supplies the recording key. Alternate uploads can escape deduplication when the available evidence is inconclusive.
- **Feedback.** Record song-level Keep and Reject plus optional overall satisfaction and comments. The interface asks users to omit identifying details. A play click is an attempt to listen.
- **Primary task outcome.** Compare each participant's keep rate in rounds where both panels show at least one song. The full-session export also reports keep rates for each arm and separates unfilled slots, unavailable panels, and rounds where an arm does not apply. Participants end the session whenever they want. Round five offers an optional satisfaction check, and the final rating remains separate.
- **YouTube Music baseline.** Use public community playlist search for text-only rounds and native playlist suggestions for playlist-only rounds. Leave the panel in its assigned position for combined rounds, with an explanation that it supports each input separately. Combined rounds still contribute to the session record.
- **LLM provider.** Use OpenRouter for the pilot. DeepSeek V4 Flash 0731 is the initial low-cost, versioned model with structured output and reasoning disabled to reserve its output budget for the song list. The app requests zero-data-retention providers, denies provider data collection, and requires support for submitted API parameters. This is a different model from the Qwen offline baseline.
- **Hosting.** The AWS CPU instance runs the app, encoder, retrieval worker, and SQLite. The existing AWS-provided CloudFront HTTPS address serves the paired study; the retrieval-only preview and private acceptance app keep separate feedback databases. Spandan facilitates the first two real sessions and owns the live export after one or two days of collection. Delete the feedback database December 15 after reviewing the export.

## Implementation choices to review

- **First participant pilot.** Aim for two completed facilitated sessions, one per pairing. Use them to check the flow and feedback export. Plan the full study's sample size separately.
- **Assignment.** Balance baseline assignments in randomized blocks of two and randomize each session's panel positions independently. Panel labels hide recommender names. Report the paired comparison at participant level because rounds and mirrored decisions within a session are dependent.
- **Audio model.** Use the existing 1.03M-track CLAP MPD HNSW index for candidate search, with exact FAISS as a selectable reference. Retrieve 100 candidates and rank the shortlist exactly. Combined requests retrieve by text and rescore with 80% text similarity and 20% mean seed similarity. Playlist-only uses mean seed similarity. These pilot settings need independent relevance evidence.
- **Seed coverage.** Match YouTube IDs in existing audio caches or match title, artist and available duration against the indexed catalog. Ambiguous recordings lack a badge. One mapped seed is sufficient. With no eligible seeds, the audio arm can serve text requests. Playlist-only audio retrieval returns an empty panel. The badge says “Can guide recommendations” because it indicates coverage.
- **Playlist-only suggestions.** Create a temporary private playlist on the team account containing the current song IDs. Reuse the offline baseline's contents verification and native suggestion fetch. Attempt deletion after each round and log the playlist ID if cleanup cannot be confirmed. The participant notice describes the temporary copy. Account writes require the team account's browser credentials.
- **Playback.** Open a YouTube embed on each Play click. Provide a direct YouTube Music link and, for ISRC-linked recordings, an optional Deezer preview. Deezer may have no preview for a matched recording. Play is never required to submit a judgment.
- **Storage.** Use SQLite on the study instance and a pseudonymous session cookie. Store panel order, each offered recording and rank, decision, play clicks, input mode, seed counts, latency, final playlist and optional feedback. Raw requests and raw search queries are processed in memory. Rehearsal, private acceptance, preview, and public study data use separate files.
- **App.** Flask and browser-native HTML, CSS and JavaScript fit the existing Python codebase. The CPU CLAP encoder and FAISS run in separate processes because the existing environments have an OpenMP conflict. The app submits both panels in parallel and records an unavailable or empty panel separately.
